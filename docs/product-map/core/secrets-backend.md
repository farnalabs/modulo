# Secrets Backend — Pluggable Secret Storage The `SecretsBackend` ABC defines a uniform interface (`get_secret`, `set_secret`, `delete_secret`) for encrypting and storing connector credentials, model backend API keys, and other sensitive values. Three implementations exist: **Fernet** (default, DB-backed), **HashiCorp Vault** (KV v2), and **AWS Secrets Manager** — selected via `MODULO_SECRETS_BACKEND` env var or the `create_secrets_backend()` factory. ## Behaviours ### Happy path - [ ] `get_secret` retrieves a previously stored plaintext value for an existing key - [ ] `set_secret` stores a new key-value pair, encrypting the value at rest - [ ] `set_secret` overwrites an existing key with a new value (upsert semantics) - [ ] `delete_secret` removes the record for an existing key - [ ] Fernet backend: encrypted value round-trips through `set_secret` → `get_secret` returning the original plaintext - [ ] Factory `create_secrets_backend()` returns `FernetSecretsBackend` by default (no env var, no `backend_name`) - [ ] Factory respects the `MODULO_SECRETS_BACKEND` env var when no `backend_name` is passed - [ ] Fernet backend: `FERNET_KEY` is separate from `SECRET_KEY` (distinct cryptographic domains — JWT signing vs secret encryption) - [ ] Vault backend: reads/writes secrets under the configured `VAULT_PATH_PREFIX` - [ ] AWS backend: creates a new secret via `create_secret`, updates existing via `update_secret` - [ ] AWS backend: `verify` credential path on delete (7-day recovery window, no force-delete) ### Edge cases - [ ] `delete_secret` is a no-op when the key does not exist (all three backends) - [ ] `set_secret` on a previously deleted key creates a fresh record (no tombstone conflict) - [ ] Fernet backend: org ID is cached after the first `_read_org_id_from_session` call and reused on subsequent operations - [ ] Factory: `fernet_key` is `None` for Vault/AWS backends (not required) - [ ] Factory: `backend_name` is case-insensitive and whitespace-trimmed - [ ] Vault backend: secret path is constructed as `{VAULT_PATH_PREFIX}/{key}` - [ ] AWS backend: `SecretBinary` decoded as UTF-8 fallback (not just `SecretString`) - [ ] Fernet backend: `set_session()` can replace the DB session after construction ### Error states - [ ] `get_secret` with a non-existent key raises `KeyError` (all three backends) - [ ] `get_secret` on corrupted/undecryptable data raises `ValueError` (Fernet backend, `InvalidToken`) - [ ] Any operation on Fernet backend without a DB session raises `RuntimeError` - [ ] `set_secret` without RLS org context set raises `RuntimeError` (Fernet backend) - [ ] Factory with unknown `backend_name` raises `ValueError` - [ ] Factory with `backend_name="fernet"` and `fernet_key=None` raises `ValueError` - [ ] Vault backend without `VAULT_ADDR` raises `ValueError` at construction - [ ] Vault backend without `VAULT_TOKEN` or `VAULT_ROLE_ID`+`VAULT_SECRET_ID` raises `RuntimeError` on first use - [ ] Vault backend on `read_secret_version` with `InvalidPath` raises `KeyError` - [ ] Vault backend on `read_secret_version` with `Forbidden` raises `PermissionError` - [ ] Vault backend: missing `value` key in Vault response raises `KeyError` - [ ] AWS backend: `ResourceNotFoundException` on `get_secret` raises `KeyError` - [ ] AWS backend: `AccessDeniedException` on `get_secret` raises `PermissionError` - [ ] AWS backend: neither `SecretString` nor `SecretBinary` in response raises `KeyError` - [ ] Vault and AWS backends raise `RuntimeError` at construction if optional dependency (`hvac` / `boto3`) is not installed ### Security - [ ] Secrets are never logged or returned in API responses - [ ] **Credential-in-state rule**: decrypted credentials must never enter LangGraph `StateGraph` state, checkpoint blobs, OTel span attributes, or log output — enforced by code review and lint rules - [ ] Fernet: secrets encrypted at rest in `secrets` table via `cryptography.fernet.Fernet` - [ ] Fernet: wrong `FERNET_KEY` cannot decrypt existing secrets (cryptographic isolation) - [ ] Vault and AWS backends delegate all encryption/access control to the external service - [ ] Implied: no secret value appears in exception messages, tracebacks, or span attributes (enforced by ABC contract) - [ ] Fernet backend uses `pg_insert` with `on_conflict_do_update` scoped to `(organisation_id, key)` — prevents cross-org key collisions ### Concurrency - [ ] All backend methods are async-safe (no shared mutable state across coroutines) - [ ] Fernet backend: `_org_id` cache is read-only after initial write per instance — safe under single-threaded asyncio - [ ] Vault/AWS backends: `_client` is lazily initialised once; subsequent calls use the cached client - [ ] Fernet backend upserts are atomic via `on_conflict_do_update` (Postgres row-level locking) ### Backward compatibility - [ ] `FernetSecretsBackend` preserves existing `secrets` table schema and encryption format - [ ] Factory default remains `fernet` — no config change needed on upgrade - [ ] Vault and AWS backends are opt-in via env var — existing deployments unaffected - [ ] Key rotation (re-encrypt with new `FERNET_KEY`) must not require JWT session invalidation, and vice versa ## Known Gaps - PRD 7.13: start-up validation of `FERNET_KEY` (absent or < 32 bytes refuses to start) — not yet implemented in code - PRD 7.13: key rotation — Fernet backend alpha limitation; no rotation mechanism exists - PRD 7.13: pluggable Vault/AWS backends marked as v2 — factory and implementation code exist but may not be wired into all consuming paths - PRD 7.13: credential-in-state lint rule not yet implemented - No BDD coverage for Vault or AWS backends (only Fernet credential_store.feature exists)
