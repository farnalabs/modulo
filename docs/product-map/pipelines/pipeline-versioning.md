# Pipeline Versioning ## Behaviours ### Snapshot Creation - [ ] Snapshot is created at run-start with a frozen copy of the live pipeline graph - [ ] Snapshot includes all connector bindings, schema version pins, prompt version pins, and model backend pins - [ ] Locking the pipeline row makes snapshot version allocation atomic with respect to concurrent graph replacement - [ ] Snapshot version is auto-incremented (max existing version + 1) per pipeline - [ ] `graph_json` stores serialised nodes (agent_id, connector_binding) and edges (edge_type, hitl_gate_config) - [ ] `connector_bindings_json` stores human-readable instance_name for historical display - [ ] `prompt_pins_json` stores SHA-256 hash of prompt_template and `updated_at` timestamp - [ ] `schema_pins_json` stores schema_id, version, and abstract_name for each referenced schema - [ ] `model_backend_pins_json` stores model_backend_id and model_id for cost calculation - [ ] `run_context_defaults` is copied from the pipeline at snapshot time - [ ] Credentials are not copied into snapshot — connector/model pins reference by ID only - [ ] Created by user_id is recorded (nullable for trigger-initiated runs) - [ ] Missing pipeline returns None (no crash) ### Run Isolation - [ ] Active runs execute against their snapshot — live pipeline changes do not affect in-progress runs - [ ] Runs started before a snapshot is replaced continue using the snapshot they were created with - [ ] UI displays a warning when a user edits a pipeline while a run is `awaiting_human` - [ ] Pipeline is locked (`SELECT ... FOR UPDATE`) during snapshot creation to prevent concurrent graph replacement ### Snapshot Querying - [ ] Snapshots can be listed for a pipeline, ordered by version descending - [ ] Listing supports pagination (page, page_size) and returns total count - [ ] Individual snapshot can be retrieved by ID with full graph detail - [ ] Snapshots display their version number prominently in the admin UI - [ ] Snapshots created_at timestamp is recorded and displayable ### Tagging and Notes - [ ] Snapshots can be tagged with an optional string (max 100 chars) - [ ] Snapshots can have optional notes (max 2000 chars) - [ ] Tags and notes can be updated after creation ### Team Ownership Changes - [ ] Changing pipeline's `owner_team_id` is blocked while any non-terminal run exists (`pending`, `running`, `awaiting_human`, `waiting_for_lock`) - [ ] ViewModel returns `pipeline_has_active_runs` to gate UI - [ ] After ownership change, UI warns that old snapshots reference connectors from previous team - [ ] Old snapshots remain valid for historical run records after ownership change - [ ] Old snapshots should not be used to start new runs after connector rebinding ### Reference Integrity - [ ] Schemas are stored by ID + version (not embedded) — deletion protection is the integrity guarantee - [ ] Pipeline FK has `ON DELETE RESTRICT` — prevents deletion of pipeline with existing snapshots - [ ] User FK has `ON DELETE SET NULL` — snapshot survives user deletion - [ ] Environment profile FK has `ON DELETE SET NULL` - [ ] Unique constraint on (pipeline_id, snapshot_version) prevents duplicate version numbers ### Error States - [ ] Snapshot creation fails gracefully if pipeline is not found (returns None) - [ ] Snapshot creation fails if a referenced agent, connector, schema, or model backend is missing - [ ] Concurrent snapshot creation for the same pipeline is serialised via row lock - [ ] Missing or null environment_profile_id is handled (field is nullable) ## Known Gaps - No BDD feature files exist for pipeline versioning — all test coverage is in unit tests - No integration tests for the full snapshot → run → live-edit → isolation lifecycle - No concurrency tests for simultaneous snapshot creation and pipeline edit - Missing UI behaviour specs for snapshot version display in pipeline history view - Missing deletion protection lifecycle: what happens to snapshots when a referenced schema version is deprecated? - No coverage for snapshot creation boundary: what happens if graph has 0 nodes?
